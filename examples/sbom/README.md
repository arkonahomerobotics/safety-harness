# Software Bill of Materials

A CycloneDX 1.5 SBOM for the `safety-harness` distribution, generated by
[`safety_harness/sbom.py`](../../safety_harness/sbom.py) from installed-package metadata -- not
hand-typed. See that module's docstring for why CycloneDX over SPDX, and for why the honest answer
here is **one** runtime third-party dependency (`pyyaml`, used by `action_schema.py` to load the
YAML action-schema config), not zero, despite `integrity.py`'s own docstring describing the package
in "dependency-free" terms.

`tests/test_sbom.py` is what actually enforces this stays honest: `DependencyDriftTest` fails if a
future change adds a runtime dependency to `pyproject.toml` without a matching, deliberate update
to that test's expected list, and `CheckedInReferenceSbomTest` fails if the file in `results/` below
drifts from what `generate_sbom()` produces today.

## Regenerate

```bash
pip install -e .                                        # same prerequisite as running tests
python -m safety_harness.sbom > examples/sbom/results/safety-harness.cyclonedx.json
```

`results/safety-harness.cyclonedx.json` is that command's real output, checked in as evidence
rather than described. Regenerate it (and re-run the test suite) after any change to
`pyproject.toml`'s `[project].dependencies` or to `safety_harness/action_schema.py`'s imports.

Set `SOURCE_DATE_EPOCH` (unix seconds) to make the output byte-identical across runs against the
same installed environment -- the only field that otherwise varies run to run is
`metadata.timestamp`.

## What's deliberately not here

- **Dev/test tooling** (`pytest`). It never ships in the installed distribution, and -- a real
  finding, not a hypothetical -- `pyproject.toml` doesn't declare it anywhere either (no
  `[project.optional-dependencies]` group exists yet). Recorded as a `metadata.properties` entry in
  the generated document rather than silently matching what a reader might expect to see.
- **Transitive dependencies of `pyyaml` itself.** It has none at the time of writing;
  `sbom.py`'s dependency walk is written to follow them automatically (BFS over
  `importlib.metadata` `requires`) if that ever changes, so this note is a snapshot, not a promise.
- **A vulnerability scan.** This SBOM states what's in the software, not whether any of it has a
  known CVE -- that's a separate, ongoing activity (`SECURITY.md` at the repo root covers how a
  vulnerability, in a dependency or in this project's own code, gets reported and handled), not
  something a point-in-time generated file can claim to guarantee.
